# Bundle Size 최적화로 50% 감소 달성하기

> 6개월간 홀로 진행한 회사 프로젝트 Bundle Size 50% 감소 프로젝트 회고입니다.

## 문제 상황

> 담당한 프로젝트의 Bundle Size가 너무 컸습니다. 특히 몇 년간 방치되어 있던 무거운 Third-party Library들이 주요 원인이었습니다!

당시 상황은 다음과 같았습니다.

- **무거운 Third-party Library들이 수년간 방치**

  - moment.js (67KB), lodash (71KB), lottie (158KB) 등이 그대로 사용 중이었습니다.
  - 더 가벼운 대안이 있음에도 불구하고 교체 작업이 이뤄지지 않았습니다.

- **구조적 문제로 인한 복잡성**

  - 현업에서 운영하는 모든 컴포넌트들이 dynamic import 형태로 구현되어 있었습니다.
  - 이로 인해 참조 추적이 어려워 어떤 컴포넌트가 실제로 사용되고 있는지 파악하기 매우 어려웠습니다.😢

- **미사용 코드들의 누적**
  - 불필요한 dynamic import component들이 계속 쌓여있었습니다.
  - 미사용 페이지들도 여전히 번들에 포함되어 있었습니다.

## 해결 과정

> 구조적 문제와 레거시 코드들로 인해 혼자서 6개월간 지속적으로 작업해야 했습니다.

### 1. Third-party Library 교체 작업

가장 임팩트가 큰 무거운 라이브러리들을 우선적으로 교체했습니다.

- **moment.js → day.js 교체**

  - 67KB에서 2KB로 97% 감소
  - 기존 코드의 moment API 사용 패턴을 day.js로 마이그레이션

- **lodash → lodash.es 교체**

  - 71KB에서 24KB로 66% 감소
  - tree-shaking이 가능한 lodash.es로 변경하여 사용하지 않는 함수들 제거

- **lottie → lottie-light-web 교체**
  - 158KB에서 34KB로 78% 감소
  - 필요한 기능만 포함된 light 버전으로 교체
  - lottie와 같은 큰 라이브러리의 경우 dynamic import 방식으로 전부 교체하여 초기 번들 크기 최적화

### 2. 미사용 코드 제거 작업

> 가장 어려웠던 부분이었습니다. dynamic import로 구현된 모든 컴포넌트들의 참조 추적이 매우 어려웠습니다.

- **dynamic import component 조사**

  - 각 컴포넌트의 실제 사용 여부를 하나하나 확인
  - 코드 분석만으로는 한계가 있어 실제 서비스 운영 데이터와 교차 검증

- **PO와의 지속적인 협업**
  - 기획적으로 더 이상 사용하지 않는 페이지들을 PO와 함께 확인
  - 비즈니스 요구사항 변경으로 인해 불필요해진 기능들 파악
  - 6개월간 꾸준히 소통하며 안전하게 제거할 수 있는 코드들 선별

### 3. 지속적인 모니터링과 검증

- **단계적 적용**

  - 한 번에 모든 변경사항을 적용하지 않고 단계별로 진행
  - 각 단계마다 서비스 영향도 검증

- **번들 분석 도구 활용**
  - webpack-bundle-analyzer를 통한 지속적인 모니터링
  - 변경 사항이 실제 번들 크기에 미치는 영향 측정

## 결과

**6개월간의 작업을 통해 담당 프로젝트의 bundle size 50% 감소를 달성했습니다.**

| 구분                  | 디바이스 | Before  | After   | 감소량  | 감소율 |
| --------------------- | -------- | ------- | ------- | ------- | ------ |
| 총 페이지(매장)       | PC       | 64.44MB | 29.94MB | -34.5MB | -53%   |
| 총 페이지(매장)       | Mobile   | 39.98MB | 28.88MB | -11.1MB | -24.4% |
| 사내 공용 node module | PC       | 2.16MB  | 1.46MB  | -0.7MB  | -32.4% |
| 사내 공용 node module | Mobile   | 3.73MB  | 2.82MB  | -0.91MB | -24.4% |

### 추가적인 성과

- **유지보수성 향상**
  - 사용 여부가 불분명했던 컴포넌트 모두 정리
  - 불필요한 코드 제거로 인한 코드베이스 정리
  - 향후 새로운 기능 추가 시 더 나은 구조적 기반 마련

## Lessons Learned

> 레거시 코드 정리는 시간이 오래 걸리지만 반드시 필요한 작업입니다.

- **지속적인 관리의 중요성**: Third-party Library들을 정기적으로 점검하고 업데이트하는 것이 중요
- **구조적 설계의 중요성**: dynamic import 사용 시 참조 추적이 가능한 구조로 설계 필수/
